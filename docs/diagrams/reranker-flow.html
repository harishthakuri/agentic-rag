Ask: the reranker sits between search and the answer

On every Ask question, the reranker is step 6. It runs once, after the search and before the writer, so the writer only sees passages that were judged to answer the question.

Safety nets

Reranker fails or times out? Search order is used instead; you still get an answer.

Nothing passes the bar? You get “I couldn’t find this in the documents”; the writer is never asked to guess.

Agent: the reranker is skipped by default

Agent mode uses the same search as Ask, but the chat AI plans the searches and reads the results itself, so the reranker step is left out unless it is switched on.

AGENT MODE · THE AI DECIDES WHAT TO SEARCH · up to 6 searches
1
Ask a question
“Compare GIN and GiST indexes for full-text search.”
2
AI plans a search
Picks its own search words, e.g. “GIN index”.
gpt-oss
3
Search two ways
Same search as Ask, but only the best 5 are returned.
4
Reranker
Skipped by default (AGENT_RERANK=false).
5
AI reads the results
Enough? Then answer. Missing a part? Search again (step 2).
gpt-oss
6
Write the answer
Cites [n] from everything it found; citations are checked.
gpt-oss
Steps 2 → 5 can repeat: one search per part of a two-part question is typical.
Why it is off: time adds up

Ask reranks once. The agent may search up to 6 times. With the reranker on, each search would wait another 1–9 seconds, so one question could take up to a minute longer.

Why it is not needed as much

In Agent mode the chat AI already reads every passage it gets back and decides whether it is useful. In a way, the agent is its own reviewer.

It also sees fewer passages per search (5, not 10), so there is less noise to sort.

It can be switched on

Set AGENT_RERANK=true. Every agent search then goes through the reranker, exactly like step 6 on page 2.

Worth trying once the fast cross-encoder reranker is in use (~1–2 s per search instead of up to ~9 s).

Upload (inward): the reranker is never used

A new document is prepared so it can be searched later. The reranker plays no part: it judges passages against a question, and at upload there is none.

At upload: passage → fingerprint
stored, reused for every question

Compare fingerprints
very fast, even over all passages
THE RERANKER · needs both at once, so it can only run when a question arrives
question
+
one passage
read together
word by word, against each other
one score
for this pair only; nothing to store
Why “never” at upload

The fingerprint can be prepared in advance. A passage’s fingerprint does not depend on who asks what, so it is made once at upload.

The reranker’s score cannot. It is a judgement about one specific question and passage pair. The questions are unknown at upload time, so there is nothing to score and nothing worth saving.

That is also why the reranker is only used on the top 10 search results: reading pairs is slow, so it reviews a shortlist, never the whole library.

In the code: the worker and the command-line tools never load the reranker. Only the API server does, at startup.

Evaluation: measuring whether the reranker helps

The evaluation is a test bench, not a user feature. It runs the same questions through search with and without the reranker, so we can see what the extra seconds buy.

1
Test questions

2a
Search without reranker
vector · keyword · hybrid

Score each ranking

5
Answer check (optional)
Full Ask and Agent answers, graded by an AI judge.
gpt-oss as judge
Benchmark result: 31 answerable questions
SetupFound in top 5Rank-1 score (MRR)Time
Hybrid search, no reranker 0.77 0.680.3 s
+ LLM reranker (gpt-oss) 0.88 0.918.5 s
+ Qwen3-Reranker-0.6B (cross-encoder) 0.88 0.872.2 s
+ bge-reranker-v2-m3 (cross-encoder) 0.83 0.841.2 s

Both scores run from 0 to 1; higher is better. MRR 1.0 = the right section is always first; 0.5 = typically second. Differences under ~0.04 are within noise for 31 questions.

What it showed
  • Every reranker helps a lot: the right section reaches rank 1 far more often (MRR 0.68 → 0.84–0.91).
  • Qwen3 ≈ the LLM reranker in quality, about 4× faster.
  • A reranker can only re-order what search found: if the right passage is not in the top 10, no reranker can fix it.
What the evaluation does not do

It never changes the app or the documents. It reads the same search code real users get, runs it with and without the reranker, and writes a report under evals/results/.

For engineers: which reviewer, settings and code

One setting chooses the reviewer. The rest of the app does not care which one: search calls whatever reranker it is given.

Two possible reviewers, one switch
RERANKER=Who reviewsScoreBar for /askSpeed
llm
code default		The chat model gpt-oss (also the writer), grading in batches of 100–3grade ≥ 1~3–9 s
cross_encoder
our .env		Qwen3-Reranker-0.6B, a small dedicated model run inside the API via sentence-transformers0–1score ≥ 0.02~1–2 s
noneNobody: search order is used as is—no filter0 s

They score on different scales, so each has its own bar. Speeds are for 10 passages on an M1 Max.
